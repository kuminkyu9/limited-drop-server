# Limited Drop

한정판 상품 판매 플랫폼 백엔드 프로젝트입니다.  
판매자는 상품을 등록하고, 사용자는 선착순 상품을 조회하거나 추첨 상품에 응모할 수 있도록 설계했습니다.

## 프로젝트 소개

Limited Drop은 한정판 상품 판매를 위한 백엔드 서비스입니다.  
공통 상품 정보를 중심으로 상품 타입별 상세 정보를 분리하여, 선착순 판매와 추첨 판매를 각각 독립적인 도메인으로 관리할 수 있도록 설계했습니다.

이 프로젝트에서는 다음과 같은 흐름을 구현했습니다.

- 회원가입 / 로그인
- JWT 기반 인증
- Refresh Token 관리
- 상품 공통 정보 관리
- 상품 옵션 관리
- 상품 이미지 업로드
- 선착순 상품 등록 / 조회
- 추첨 상품 등록 / 조회
- 추첨 응모 기능
- 상품별 1인 1응모 정책 검증

---

## 프로젝트 목표

단순한 CRUD 구현이 아니라,  
도메인 구조를 분리하고 데이터 정합성을 고려한 백엔드 MVP를 만드는 것을 목표로 했습니다.

특히 아래 내용을 중요하게 생각하며 설계했습니다.

- 상품 공통 정보와 타입별 상세 정보 분리
- 판매자 / 일반 사용자 역할 분리
- 인증이 필요한 기능에서 로그인 사용자 식별
- 잘못된 요청을 막기 위한 검증 로직 적용
- 이후 주문, 장바구니, 찜 기능으로 확장 가능한 구조 설계

## 주요 기능

### 1. 회원 인증

- 회원가입 API 구현
- 로그인 API 구현
- JWT Access Token 발급
- Refresh Token 발급 및 별도 관리
- 인증 객체를 통해 로그인 사용자 식별

### 2. 상품 공통 구조

- `products` 테이블에서 상품 공통 정보 관리
- 판매자(`SELLER`)가 상품 등록
- 상품명, 브랜드, 가격, 설명, 판매자 정보 저장
- 공통 상품을 기준으로 옵션, 이미지, 타입별 상세 정보 연결

### 3. 상품 옵션

- 상품과 옵션을 1:N 구조로 설계
- 옵션별 사이즈, 재고 수량, 판매 수량 관리
- 선착순 상품 / 추첨 상품 모두 공통 옵션 구조 재사용

### 4. 상품 이미지 업로드

- AWS S3를 활용한 이미지 업로드 기능 구현
- 업로드된 이미지 URL을 DB에 저장
- 상품 상세 조회 시 이미지 목록 함께 제공

### 5. 선착순 상품

- 선착순 상품 생성 API
- 선착순 상품 목록 조회 API
- 선착순 상품 상세 조회 API
- 판매 시작/종료 시간, 총 수량, 판매 수량, 판매 상태 관리

### 6. 추첨 상품

- 추첨 상품 생성 API
- 추첨 상품 목록 조회 API
- 추첨 상품 상세 조회 API
- 응모 시작 시간, 응모 종료 시간, 발표 시간, 당첨자 수 관리
- 추첨 상태를 기준으로 응모 가능 여부 판단

### 7. 추첨 응모

- 추첨 응모 등록 API
- 로그인 사용자 기준 응모 처리
- 상품별 1인 1응모 정책 적용
- 선택한 옵션이 해당 상품 소속인지 검증
- 응모 가능 시간 / 상태 검증 후 저장

## 도메인 설계

이 프로젝트의 핵심은 **공통 상품 구조 + 타입별 상세 정보 분리**입니다.

### 상품 구조

- `products`
  - 모든 상품이 공통으로 가지는 기본 정보 관리
- `fcfs_products`
  - 선착순 상품 전용 상세 정보 관리
- `raffle_products`
  - 추첨 상품 전용 상세 정보 관리
- `product_options`
  - 상품 옵션별 재고 / 수량 관리
- `product_images`
  - 상품 이미지 정보 관리
- `raffle_entries`
  - 추첨 응모 내역 관리

### 설계 의도

상품 공통 정보는 `products`에 모으고,  
상품 타입별 규칙은 별도 테이블로 분리하여 다음과 같은 장점을 얻고자 했습니다.

- 공통 기능을 `products` 기준으로 일관되게 연결 가능
- 선착순 / 추첨 도메인 규칙을 독립적으로 관리 가능
- 옵션, 이미지, 찜, 장바구니, 주문 기능 확장에 유리
- 유지보수성과 확장성 향상

## 데이터 정합성 고려 사항

이 프로젝트에서는 데이터 정합성을 중요하게 생각했습니다.

- 모든 테이블은 PK를 가짐
- FK는 특별한 이유가 없으면 NOT NULL 기준으로 설계
- 상품 생성 주체는 `SELLER`
- `products.seller_id`는 `users.id`를 참조
- 응모 시 상품-옵션 관계 검증
- 동일 사용자의 상품별 중복 응모 방지
- 인증이 필요한 요청은 로그인 사용자 기준으로 처리

즉, 단순히 저장되는 API가 아니라  
잘못된 요청을 먼저 차단하는 API를 만드는 데 집중했습니다.

## API 예시

### 인증 / 회원
- `POST /auth/signup` : 회원가입
- `POST /auth/login` : 로그인
- `POST /auth/refresh` : 토큰 재발급

### 선착순 상품
- `POST /fcfs-products` : 선착순 상품 생성
- `GET /fcfs-products` : 선착순 상품 목록 조회
- `GET /fcfs-products/{productId}` : 선착순 상품 상세 조회

### 추첨 상품
- `POST /raffle-products` : 추첨 상품 생성
- `GET /raffle-products` : 추첨 상품 목록 조회
- `GET /raffle-products/{productId}` : 추첨 상품 상세 조회

### 추첨 응모
- `POST /raffle-products/{productId}/entries` : 추첨 응모

> 실제 엔드포인트는 프로젝트 구현 기준에 맞게 수정해서 사용하면 됩니다.

## 응답 설계 포인트

목록 조회와 상세 조회의 목적이 다르기 때문에 DTO를 분리해서 설계했습니다.

- 목록 조회 DTO
  - 상품명, 가격, 대표 이미지, 상태 등 요약 정보 중심
- 상세 조회 DTO
  - 설명, 옵션 목록, 이미지 목록, 판매/응모 정보 등 상세 정보 포함

이렇게 분리하면 필요한 데이터만 내려줄 수 있어 응답 구조를 더 명확하게 관리할 수 있습니다.

## 구현하면서 중점적으로 고민한 부분

### 1. 공통 상품 구조 설계
상품마다 공통으로 필요한 정보와,  
선착순/추첨처럼 타입별로 다른 정보를 어떻게 나눌지 고민했습니다.

그 결과, `products`를 중심 테이블로 두고  
타입별 상세 정보를 별도 테이블로 분리하는 구조를 선택했습니다.

### 2. 인증 사용자 기반 처리
상품 생성, 추첨 응모처럼 사용자 정보가 필요한 기능은  
JWT 인증을 통해 로그인 사용자를 식별해서 처리했습니다.

### 3. 비즈니스 검증 우선
추첨 응모 기능에서는 아래 순서로 검증 후 저장하도록 구현했습니다.

1. 로그인 사용자 확인
2. 해당 상품이 추첨 상품인지 확인
3. 현재 응모 가능한 시간 / 상태인지 확인
4. 선택한 옵션이 해당 상품 소속인지 확인
5. 이미 응모한 이력이 있는지 확인
6. 조건 충족 시 응모 저장
